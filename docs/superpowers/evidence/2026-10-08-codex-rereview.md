## R1부터 R3까지 확인한 결과

### R1 전송 차단 확인

`remote.report_job`은 `steps.upload == "skipped"`일 때 설정을 읽거나 요청을 보내기 전에 반환한다. 새 테스트는 작업 시작·단계 변경·종료와 실제 `fetch(upload=False)` 경로를 확인한다.

현재 428개 테스트에서 두 회귀 테스트가 통과했다. 추가로 `6226c56`의 이전 `report_job` 함수만 메모리에 불러와 동일한 두 테스트를 실행했을 때 정확히 2개가 실패했다. 수정이 해당 결함을 막는다는 근거다. 기존 업로드 대상 작업의 정상 보고 테스트도 통과했다.

### R2 재시도 상태와 서버 검사 확인

`upload.main`을 통해 첫 업로드 실패, 재시도 실패, 최종 성공을 순서대로 실행했다. 네트워크 업로드는 합성 성공·실패로 대체하고, 진행 기록은 복사해 매번 실제 `check_job`과 `HostedStore.put_job`에 넣었다.

| 시점 | 전체 상태 | upload 단계 | 오류·상세 | 서버 검사 |
|---|---|---|---|---|
| PC 저장 후 업로드 대기 | running | pending | 오류 없음, 업로드 대기 | 통과 |
| 업로드 시작 | running | running | 오류·실패 상세 없음 | 통과 |
| 첫 업로드 실패 | done | failed | 첫 오류 보존, PC 저장 완료·업로드 실패 | 통과 |
| 재시도 시작 | running | running | 이전 오류와 실패 상세 제거 | 통과 |
| 재시도 실패 | done | failed | 이번 오류로 교체, 실패 상세 복원 | 통과 |
| 다시 재시도 | running | running | 오류·실패 상세 제거 | 통과 |
| 최종 성공 | done | done | 오류 없음, 상세 빈 값 | 통과 |

실패 후에는 `pending_upload_job`이 같은 작업을 찾으며 최종 성공 후에는 찾지 않는다. `check_job`은 전체 상태와 개별 단계의 허용 값·필드 형식을 검사하며, `done + upload failed + error 문자열`을 금지하지 않으므로 충돌하지 않는다. 실제 Railway 주소에 대한 검증은 아니다.
